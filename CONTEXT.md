# MySkills

MySkills centralizes the skills selected for personal ownership while keeping discovered
but unapproved skills outside its management boundary.

## Language

**Candidate Skill**:
A skill discovered in a source repository or local installation that is awaiting an explicit management decision.
_Avoid_: Installed skill, managed skill

**Skill Origin**:
The repository or installation from which a Candidate Skill was discovered.
_Avoid_: Skill category, ownership

**Skill Category**:
The functional bucket under `skills/` in which a Managed Skill belongs, independent of where it originated.
_Avoid_: Skill origin, repository

**Managed Skill**:
A skill explicitly accepted into MySkills as its authoritative, editable copy.
_Avoid_: Candidate skill, discovered skill

**Provenance**:
The source repository, source commit, import date, and ownership record retained for an imported Managed Skill.
_Avoid_: Git history, installation source

**Executable Policy**:
A governance rule enforced by a manifest schema, CLI guard, validator, or automated test rather than relying on documentation alone.
_Avoid_: Guideline, undocumented convention

**Explicit-invocation Skill**:
A Managed Skill that enters a workflow only after the human explicitly names or invokes it; the AI must not select it implicitly on any supported platform.
_Avoid_: Human-only Skill, manual Skill

**Implicit-invocation Skill**:
A Managed Skill that the AI may select from the task context and Skill description without the human naming it; explicit invocation remains valid, and the classification is the same on every supported platform.
_Avoid_: Automatic Skill, AI-only Skill

**Skill Dependency**:
A third-party executable, runtime, CLI, or package required for a Managed Skill to work on a supported computer.
_Avoid_: Skill, bundled tool

**Runtime Prerequisite**:
A user-provided runtime whose presence and minimum version MySkills verifies but does not install. A missing or incompatible prerequisite blocks only the affected installation.
_Avoid_: Managed dependency, bundled runtime

**Installable Dependency**:
A third-party tool that MySkills is allowed to install after its required Runtime Prerequisites pass validation.
_Avoid_: Runtime prerequisite, bundled tool

**Machine Setup**:
The PowerShell-based, single-command process that installs eligible Managed Skills and their installable Skill Dependencies on another supported computer. It reports and skips installations whose Runtime Prerequisites are missing or incompatible.
_Avoid_: Bootstrap, skill copy, manual setup

**Supported Computer**:
A Windows computer on which MySkills guarantees that its installation and dependency-management workflows work.
_Avoid_: Any computer, cross-platform host

**Implementation-Ready Task**:
A specification-package work unit containing one Reviewable Capability that one AI can implement, validate, and hand off for focused human code review while preserving the approved behavior and applicable project rules.
_Avoid_: Small task, ticket, technical-layer task

**Eligible Task**:
An Implementation-Ready Task whose current, non-superseded specification items and Task Execution Manifest pass readiness, whose mutable Task Lifecycle State permits execution, and whose dependencies have all been accepted by a human.
_Avoid_: Review-ready Task, deferred dependency, AI-completed Task

**Reviewable Capability**:
A cohesive, independently testable feature centered on one user goal and one primary domain concept or lifecycle. It may include multiple closely related operations when a human can review them as one meaningful functional unit without excessive breadth.
_Avoid_: Single operation, technical layer, broad feature area

**Capability Slice**:
An independently demonstrable Reviewable Capability that leaves its related user- or system-observable behaviors working through defined validation seams.
_Avoid_: Frontend task, backend task, database task, isolated operation

**Shared Enabler**:
An independently verifiable prerequisite contract or reusable capability that serves at least two confirmed Implementation-Ready Tasks and is completed before those dependent tasks.
_Avoid_: Common code, speculative abstraction, miscellaneous setup task

**Spec Task Executor**:
An explicitly invoked workflow that implements one Implementation-Ready Task from a formal package generated by `spec-package-generator` and records validation and review evidence against that package.
_Avoid_: General implement workflow, standalone prompt runner, informal task executor

**Task Execution Session**:
The execution of exactly one eligible Implementation-Ready Task under one coordinating owner. It may use multiple collaborating workers, but produces one integrated validation and review handoff and never continues into another Task automatically.
_Avoid_: Development session, feature implementation run, task chain

**Task Work Unit**:
An internal subdivision of one Implementation-Ready Task assigned to a collaborating worker with an exclusive write scope. It is not independently accepted, does not appear as a formal Task, and remains part of the Task's single integrated review.
_Avoid_: Task, Capability Slice, separately accepted subtask

**Work Unit Brief**:
A Coordinator-derived, task-bounded instruction containing only the outcome context, source references, write scope, shared contracts, Skill use, focused validation, forbidden scope, and reporting contract needed by one Task Work Unit.
_Avoid_: Task Execution Manifest, independent specification, full feature context

**Task Coordinator**:
The single owner of a Task Execution Session that assigns non-overlapping Task Work Units, retains single-writer ownership of shared files, integrates all changes, and produces the Task's final validation and review handoff.
_Avoid_: Task worker, multiple integration owners, automatic task scheduler

**Task Execution Manifest**:
The machine-readable YAML routing contract generated by `spec-package-generator` and consumed by the Spec Task Executor. It references immutable normative inputs while owning their loading, dependencies, Skill Plan, validation, evidence destination, and freshness data without owning mutable Task Lifecycle State or redefining behavior.
_Avoid_: Final prompt, copied context, informal handoff

**Execution Freshness Policy**:
The hybrid rule that digest-pins approved specification content, excludes mutable Task Lifecycle State from those digests, and requires the Spec Task Executor to reread current project rules during Execution Preflight.
_Avoid_: Pin every source, trust every current file, ignore project-rule drift

**Skill Plan**:
The Task Execution Manifest section that classifies workflow Skills as mandatory, conditionally triggered, or executor-added. The Spec Task Executor may add justified Skills but cannot omit a mandatory Skill.
_Avoid_: Suggested Skill list, prompt hint, implicit Skill selection

**Execution Preflight**:
The human confirmation checkpoint before a Spec Task Executor modifies code. It approves the selected Task's internal Work Units, write ownership, Skill Plan, validation plan, and expected review scope without changing the approved Task itself.
_Avoid_: Specification gate, Task acceptance, implementation review

**Task Plan Gate**:
The human confirmation checkpoint after solution approval and before execution artifacts are finalized. It approves each Reviewable Capability, Shared Enabler, dependency, independent test boundary, and expected review scope.
_Avoid_: Gate 2 solution approval, Execution Preflight, Human Review Gate

**Approved Execution Boundary**:
The Task scope, Work Units, write ownership, Skill Plan, and validation plan authorized by an Execution Preflight. The Task Coordinator may work autonomously inside it until review-ready, but must stop when implementation would cross it or trigger a fail-closed state.
_Avoid_: General autonomy, specification change authority, implicit approval

**Execution Record**:
An append-only record of one Task Execution Session or Human Review revision, including its confirmed preflight, artifact versions, Work Units, Skill use, changes, validation, AI review, deviations, risks, and handoff state.
_Avoid_: Overwritten evidence, final summary, implementation-evidence index

**Integrated Task Validation**:
The Coordinator-owned validation of the complete Implementation-Ready Task after all Task Work Units are integrated. Focused Work Unit checks support it, but only this Task-level evidence can move the Task to review-ready status.
_Avoid_: Work Unit test result, individual agent success, partial validation

**Task Test Owner**:
The single writer responsible for establishing and validating the Task-level red-state acceptance expectations before implementation Work Units begin. Other workers may add focused tests but cannot weaken or independently redefine those expectations.
_Avoid_: Multiple acceptance-test owners, implementation-specific test writer, post-hoc test author

**Parallel Task Wave**:
A set of dependency-eligible Implementation-Ready Tasks executed concurrently as separate Task Execution Sessions.
_Avoid_: Task Work Units, concurrent edits without ownership, automatic task chain

**Human Review Gate**:
The mandatory pause after Task validation and AI code review have completed and all required findings are resolved. Only a human may accept the Task, and dependent development does not continue until acceptance.
_Avoid_: Automatic acceptance, AI self-approval, post-implementation summary

**Changes Requested**:
The Human Review Gate state in which an Implementation-Ready Task keeps its identity and returns for a focused revision against recorded review comments. Each revision appends validation and review evidence before returning to review-ready status.
_Avoid_: Blocked Task, replacement Task, overwritten review history

**Re-slice Required**:
The fail-closed state used when an Implementation-Ready Task is not cohesive or reviewable at its approved boundary. Only `spec-package-generator` may replace it with revised Task boundaries.
_Avoid_: Task Work Unit split, implementation workaround, blocked Task

**Spec Revision Required**:
The fail-closed state used when implementation evidence shows that authoritative behavior, solution, Task boundaries, or validation meaning must change. Lifecycle bookkeeping and execution-routing omissions do not by themselves qualify.
_Avoid_: Re-slice Required, implementation assumption, silent scope change

**Spec Change Request**:
An evidence-backed handoff produced by the Spec Task Executor when Task boundaries or authoritative specification meaning must change. It identifies the affected Task, observed evidence, return level, affected Specification Items, and partial-change state so a human can explicitly start specification revision.
_Avoid_: Automatic cross-Skill mutation, informal blocker note, executor-authored specification change

## Revision Model

These terms describe the confirmed target model. The current Skill templates have not yet been migrated to it.

**Specification Item**:
The smallest normatively meaningful unit with a stable Specification ID whose revision impact can be evaluated independently of its containing document.
_Avoid_: Specification file, arbitrary paragraph, document version

**Specification ID**:
An opaque identifier from a closed prefix schema that establishes a Specification Item's identity without encoding its category or meaning.
_Avoid_: Descriptive ID, ad hoc prefix, classification label

**Task Lifecycle State**:
The single mutable record of a Task's execution and human-review progress, maintained separately from immutable specification content and execution routing.
_Avoid_: Task definition, status copied into normative artifacts, dashboard-local state

**Revision Impact Set**:
The ID-level set of downstream Specification Items that a revision must either update, supersede, or explicitly classify as unaffected.
_Avoid_: File invalidation list, regenerate everything, informal affected-files list

**Candidate Planning Workspace**:
A durable-but-transient, non-authoritative recovery workspace for one active discussion and its consolidated application plan before an approved change is applied directly to Current. It may preserve interrupted work in the fixed Candidate roles, is neither complete nor a full-Validator target, and its question material is deleted after exact application plus permitted Decision writing; final package validation happens only after explicit finish.
_Avoid_: Second specification version, validation target, promotion source, historical archive

**Active Question Record**:
The sole definition of the one active `Q-nnn`, stored in `candidate/question.yaml` with exactly a bounded non-empty question and an answer that is null before response or bounded non-empty afterward. Every Current Specification ID token in the question is a declared change subject; context-only IDs go in Candidate discussion, and the answer may not introduce an undeclared Current ID. Plan seal requires one operation for each subject and removal of every frozen subject. Workflow State and Candidate recovery files may reference Q but never redefine it; Finalizer removes it after exact Plan reconciliation and deterministic Decision Card creation, without treating that one decision as package `pass`.
_Avoid_: Question text in Workflow State, separate affected-ID list, context-only ID in question, duplicate Q definition, completed Q history, Q in Current

**Question-Decision Sequence**:
The feature-local shared numeric sequence in which Controller atomically reserves the allocator's next `DECISION` suffix, creates active `Q-nnn`, and successful finalization writes retained `DEC-nnn` with the same suffix. Canceled/crashed reservations leave harmless gaps. Normal allocation never scans History, so Decision content and IDs do not control workflow state or the next suffix.
_Avoid_: Archive-driven allocation, separate Q file counter, constant reused Q ID, mismatched Q/DEC suffixes

**Workflow State Center**:
The single AI-facing resume and completion authority, recording exactly phase, active Q reference, and sealed-Plan fingerprint. Controller derives operation progress and next action, clears decision/repair finalization bindings, and alone sets workflow `pass` after explicit package finish, Controller completion checks, matching full `VALID`, and transient cleanup. It stores no Current fingerprint because exact target reconciliation, expected-final fingerprint, and latest Validation Result own that proof.
_Avoid_: Duplicate status files, reconciled-Current cache, persisted next-action prose, free-form progress diary, specification authority, validator retry counter

**Derived Operation Progress**:
The ephemeral completed/pending/conflict classification produced by comparing every unique-target exact-delta operation with Current. It is returned to AI by Controller but never persisted; non-prefix results such as operations 1 and 3 complete while 2 is pending remain visible.
_Avoid_: Progress cursor, OP ID, completed-operation ledger, prefix-count assumption

**Workflow Phase**:
One of exactly `discussing`, `planning`, `applying_current`, `validating`, `finalizing`, or `pass`. File Contract and Validator own enum legality; Controller alone writes and transitions it. Repair and human-help conditions remain derived actions rather than additional phases.
_Avoid_: Seventh phase, free-form phase, validator-written phase, idle/blocked/error phase

**Repair Cycle**:
One evidence-based AI correction that produces a materially different explicitly evaluated checkpoint after an `INVALID` finding. Controller proves the invalid Current still equals the evaluated result, clears Workflow State first, then replaces any stale Plan with a `basis: validation` exact repair Plan under the same attempt budget and no Q/DEC. Initial detection, unchanged reruns, and normal phase changes do not count. Validator writes attempt evidence before the latest result; the third changed repair may succeed, while a third still-invalid repair requires human intervention. `ERROR`, semantic uncertainty, non-representable repair, or unexpected Current stops immediately.
_Avoid_: Counting findings, resetting on changed error text, unlimited cross-checkpoint repair, speculative semantic repair

**Exact-Delta Application Plan**:
A temporary `candidate/application-plan.yaml` closed to exactly one question-or-validation basis, one five-class allocation baseline, one expected-final authoritative Current fingerprint, and an unordered logical set of unique target deltas. Presence is not sealing; matching Workflow State `plan_fingerprint` seals it. AI submits symbolic new-ID handles; Controller reserves/substitutes numeric IDs and proves new suffixes are exactly above the captured baseline. Every operation has the same target/before/after envelope; Controller derives creation/update/removal and per-target progress, virtually applies the Plan, then applies each complete payload so AI writes it only once. Array position has no progress meaning. The Plan is neither prose guidance, full Candidate specification, normative authority, retained history, nor old-to-new mapping ledger.
_Avoid_: Update-related-items instruction, copied Current package, AI copying payload twice, `id_transitions`, operation kind, progress cursor, raw path, whole-owner fingerprint, unsealed plan, implicit downstream change

**Current Specification Set**:
The only authoritative specification graph loaded by normal generation and execution, containing no replaced IDs or superseded normative content.
_Avoid_: Specification history, mixed-version package, candidate changes

**Current ID Index**:
The single machine-readable owner of which `REQ`, `BDD`, `DESIGN`, `TEST`, and `TASK` IDs belong to the Current Specification Set. Definition locations and relationships are discovered from owning artifacts and must not be copied into the index. Transient `Q` and cold-history `DEC` IDs are schema-governed but never enter this index.
_Avoid_: Traceability view, historical ID registry, Q/DEC membership, location map, duplicated specification content

**Specification ID Allocation State**:
The Controller-only Feature-lifetime `control/id-allocation.yaml` containing monotonic `highest_issued` integers for REQ, BDD, DESIGN, TEST, TASK, and the shared Q/DEC `DECISION` sequence. Controller captures the five Specification counters as a Plan baseline, atomically reserves symbolic new IDs as ranges, and reserves Q before creation; crash/cancel gaps remain, counters never decrement/fill/wrap, and the file is excluded from normal AI context. Every initialized Feature retains it even with no active IDs. It is allocation state, not an old-ID history.
_Avoid_: Active-index maximum, used-ID ledger, archive scan, gap reuse, AI-selected suffix

**Specification Identity Freeze**:
The rule that sealing a Plan freezes every Record in its virtual-final authoritative Current; a validated workflow `pass` is therefore also entirely frozen. Any later canonical content change removes the old ID, allocates a fresh ID, and closes all reverse references through exact Plan operations. This applies uniformly to REQ/BDD/DESIGN/TEST/TASK and does not depend on Task implementation history.
_Avoid_: Same-ID post-pass semantic edit, accepted-only freeze, reversible Task-state predicate

**ID Scope**:
The `id-schema.yaml` boundary that permits an ID class only in Current (`REQ`, `BDD`, `DESIGN`, `TEST`, `TASK`), transient Candidate/Control (`Q`), or cold History (`DEC`). An ID occurrence outside its declared scope is illegal even when its prefix and number are well formed.
_Avoid_: One global ID graph, Q/DEC in Current, scope inferred without schema

**Current Rewrite Transaction**:
The bounded application of one approved plan directly to Current, replacing all affected normative IDs, content, and references before exact Controller reconciliation. A question transaction then records its Decision and returns to the clean between-question checkpoint; only explicit package finish plus Controller completion and full Validator `VALID` permits workflow `pass`. Inactive derived Views may remain stale until their next User display.
_Avoid_: Candidate promotion, intermediate validation, untracked partial rewrite, historical retention

**Answer Application Transaction**:
The recoverable workflow step that records and plans one answered material question in Candidate, applies every required exact target delta directly to Current with progress derived from Plan-versus-Current comparison, writes the deterministic compact Decision, removes transient question material, and clears the Active Question before another question or explicit package finish. It never runs final package validation or creates `pass` by itself.
_Avoid_: Batched decision replay, archive-driven generation, answer-only recording

**Traceability View**:
A fully regenerated, non-authoritative projection of Specification ID relationships used to detect disagreement with the owning artifacts.
_Avoid_: Hand-maintained traceability source, duplicate authority, specification owner

**User Review View**:
A one-way, non-authoritative latest-only singleton rendering generated from validated current Records exclusively for human inspection or confirmation. It remains after confirmation and may stay stale while no display is requested; its bytes and ID occurrences do not participate in the authoritative Current fingerprint or removed-ID gate. Before Controller-mediated display or confirmation, the Controller compares its source fingerprint and atomically overwrites the canonical file when necessary. Direct filesystem opening has no freshness guarantee and requires no visible warning. Normal AI generation and Implementation do not use it as specification input; human feedback returns through Candidate, changes Records, and regenerates the View.
_Avoid_: Specification owner, general generated-file folder, machine-only output, editable source of truth, dated or versioned View history

**Dashboard View**:
The simplified latest-only read-only User Review View at `current/views/dashboard.html`. It shows feature name, Task count/order, and minimal Task cards with ID, title, one-line outcome, dependencies, Task/Manifest links, and a copyable Manifest-backed execution Prompt. It owns no Task state, readiness, eligibility, detailed Task contract, or specification meaning.
_Avoid_: Task lifecycle owner, readiness result, editable status board, localStorage state, Implementation input

**Active Question State**:
The minimal current workflow state for the single unresolved blocking question, removed after its answer is applied to the Current Specification Set.
_Avoid_: Permanent open-question log, resolved-question history, duplicated question owner

**Decision Archive**:
A cold, non-authoritative `history/decisions.yaml` stream with one automatically created minimum viable Decision Card for every confirmed material decision. Each card has only an archive `id` plus `content.question` and `content.decision`; adding fields requires an explicit schema migration. It is the only retained history and is excluded from normal specification loading, readiness, traceability, invalidation, resume, implementation, and Gate control.
_Avoid_: Current specification authority, resume input, permanent decision dependency

**Specification Package Validator**:
The deterministic legality checker that inventories files which actually exist and verifies their allowed role, canonical name/location, permitted multiplicity, format, content, IDs, and relationships. It does not require file presence or own workflow state, applicability, completeness, readiness, or `not-applicable` decisions.
_Avoid_: AI checklist, readiness opinion, hand-maintained report

**Validator Control State**:
The single transient JSON record outside Current containing only `repair_count` and the last explicitly evaluated `{kind, fingerprint, result}` checkpoint. It counts changed correction evaluations after an initial INVALID, never ordinary phase transitions; latest typed findings/evidence live separately in Validation Result and a file lock is only an atomic-write mechanism, not persisted state. When an INVALID episode starts/continues, Validator updates this record before the latest result; a direct VALID or ERROR does not create/advance it, and missing/malformed evidence after the first INVALID is an operational error rather than a reset.
_Avoid_: Workflow-document counter, attempt history, SQLite authority, process-memory counter

**ID Record**:
The smallest prescribed machine-readable unit that presents one identity and its schema-governed current knowledge content.
_Avoid_: Free-form ID mention, knowledge card, duplicated metadata envelope

**ID Content Schema**:
The prescribed content shape for one ID class, used to distinguish valid current knowledge from arbitrary or incomplete content.
_Avoid_: Universal metadata card, prose convention, optional template

**Normative Reference Edge**:
A schema-declared ID-valued relationship from one current ID Record to another. Every current normative content unit used as a relationship target must have an ID so the validator can derive both its dependents and dependencies.
_Avoid_: File-path dependency, heading link, copied ruling, prose-only traceability

**ID Definition Owner**:
The one schema-declared YAML multi-document file in which every current ID Record of one ID class is defined. Many consumers may reference the class, but no second file may define or relocate its records.
_Avoid_: Per-ID file, duplicated class definition, Current ID Index location map, consumer-owned copy

**Managed Package File**:
Any existing file inside the Current Specification Set that must be classified and inspected by the Specification Package Validator before it can receive `VALID`; the term does not imply that an absent role must be created.
_Avoid_: Extra file, ignored artifact, untracked specification note

**Managed Package File Role**:
The single declared classification that determines which format and validation rules apply to a Managed Package File.
_Avoid_: Broad file extension allowance, undocumented file type, overlapping role

**Package Schema**:
The Skill-bundled physical architecture catalog that maps each closed File Role to its canonical path or ID-bound leaf pattern, producer, permitted multiplicity, writer, authority, lifecycle, cleanup, and File Contract/File Guide keys. It defines where existing files are legal, not whether a file must currently exist, and is never copied into a Feature Package.
_Avoid_: File-purpose guide, parser schema, feature-local manifest, prose directory tree

**File Contract Catalog**:
The strict JSON catalog that maps a contract key to one parser, structural shape, deterministic check profile, and ID-scan mode for the Validator. It contains no paths, producers, lifecycle, or AI purpose prose.
_Avoid_: Package Schema, template, checklist, role location catalog

**File Guide**:
The concise YAML catalog that maps each File Role to its AI-facing purpose and usage guidance. The Package Controller joins it with Package Schema and File Contracts only for requested roles.
_Avoid_: Output path catalog, validation rules, workflow history, all-files prompt context

**Managed Package Root**:
The explicitly declared Current directory whose complete contents are authority-scoped and closed-world validated. Candidate planning and other files outside it are not specification authority; exact external evidence may be verified separately without scanning its containing tree.
_Avoid_: Repository-wide scan, conversation scan, flat mixed-authority feature folder, implicit extra specification file

**Feature Package Root**:
One existing `<project>/.ai-dev/features/<feature-name>/` instance whose top level is closed to exactly `current/`, `candidate/`, `history/`, and `control/`. Every child path must be implied by a Package Schema role; Skill definitions and project-scoped context are separate schema scopes.
_Avoid_: New feature-name wrapper, flat legacy package, arbitrary root file, feature-local schema copy
