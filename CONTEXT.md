# MySkills

MySkills centralizes the skills selected for personal ownership while keeping discovered
but unapproved skills outside its management boundary.

## Language

**Candidate Skill**:
A skill discovered in a source repository or local installation that is awaiting an explicit management decision.
_Avoid_: Installed skill, managed skill

**Skill Origin**:
The repository or installation from which a Candidate Skill was discovered.
_Avoid_: Skill category, ownership

**Skill Category**:
The functional bucket under `skills/` in which a Managed Skill belongs, independent of where it originated.
_Avoid_: Skill origin, repository

**Managed Skill**:
A skill explicitly accepted into MySkills as its authoritative, editable copy.
_Avoid_: Candidate skill, discovered skill

**Provenance**:
The source repository, source commit, import date, and ownership record retained for an imported Managed Skill.
_Avoid_: Git history, installation source

**Executable Policy**:
A governance rule enforced by a manifest schema, CLI guard, validator, or automated test rather than relying on documentation alone.
_Avoid_: Guideline, undocumented convention

**Explicit-invocation Skill**:
A Managed Skill that enters a workflow only after the human explicitly names or invokes it; the AI must not select it implicitly on any supported platform.
_Avoid_: Human-only Skill, manual Skill

**Implicit-invocation Skill**:
A Managed Skill that the AI may select from the task context and Skill description without the human naming it; explicit invocation remains valid, and the classification is the same on every supported platform.
_Avoid_: Automatic Skill, AI-only Skill

**Skill Dependency**:
A third-party executable, runtime, CLI, or package required for a Managed Skill to work on a supported computer.
_Avoid_: Skill, bundled tool

**Runtime Prerequisite**:
A user-provided runtime whose presence and minimum version MySkills verifies but does not install. A missing or incompatible prerequisite blocks only the affected installation.
_Avoid_: Managed dependency, bundled runtime

**Installable Dependency**:
A third-party tool that MySkills is allowed to install after its required Runtime Prerequisites pass validation.
_Avoid_: Runtime prerequisite, bundled tool

**Machine Setup**:
The PowerShell-based, single-command process that installs eligible Managed Skills and their installable Skill Dependencies on another supported computer. It reports and skips installations whose Runtime Prerequisites are missing or incompatible.
_Avoid_: Bootstrap, skill copy, manual setup

**Supported Computer**:
A Windows computer on which MySkills guarantees that its installation and dependency-management workflows work.
_Avoid_: Any computer, cross-platform host

**Implementation-Ready Task**:
A specification-package work unit containing one Reviewable Capability that one AI can implement, validate, and hand off for focused human code review while preserving the approved behavior and applicable project rules.
_Avoid_: Small task, ticket, technical-layer task

**Eligible Task**:
An Implementation-Ready Task whose package and Task Execution Manifest are current, whose readiness checks pass, and whose dependencies have all been accepted by a human.
_Avoid_: Review-ready Task, deferred dependency, AI-completed Task

**Reviewable Capability**:
A cohesive, independently testable feature centered on one user goal and one primary domain concept or lifecycle. It may include multiple closely related operations when a human can review them as one meaningful functional unit without excessive breadth.
_Avoid_: Single operation, technical layer, broad feature area

**Capability Slice**:
An independently demonstrable Reviewable Capability that leaves its related user- or system-observable behaviors working through defined validation seams.
_Avoid_: Frontend task, backend task, database task, isolated operation

**Shared Enabler**:
An independently verifiable prerequisite contract or reusable capability that serves at least two confirmed Implementation-Ready Tasks and is completed before those dependent tasks.
_Avoid_: Common code, speculative abstraction, miscellaneous setup task

**Spec Task Executor**:
An explicitly invoked workflow that implements one Implementation-Ready Task from a formal package generated by `spec-package-generator` and records validation and review evidence against that package.
_Avoid_: General implement workflow, standalone prompt runner, informal task executor

**Task Execution Session**:
The execution of exactly one eligible Implementation-Ready Task under one coordinating owner. It may use multiple collaborating workers, but produces one integrated validation and review handoff and never continues into another Task automatically.
_Avoid_: Development session, feature implementation run, task chain

**Task Work Unit**:
An internal subdivision of one Implementation-Ready Task assigned to a collaborating worker with an exclusive write scope. It is not independently accepted, does not appear as a formal Task, and remains part of the Task's single integrated review.
_Avoid_: Task, Capability Slice, separately accepted subtask

**Work Unit Brief**:
A Coordinator-derived, task-bounded instruction containing only the outcome context, source references, write scope, shared contracts, Skill use, focused validation, forbidden scope, and reporting contract needed by one Task Work Unit.
_Avoid_: Task Execution Manifest, independent specification, full feature context

**Task Coordinator**:
The single owner of a Task Execution Session that assigns non-overlapping Task Work Units, retains single-writer ownership of shared files, integrates all changes, and produces the Task's final validation and review handoff.
_Avoid_: Task worker, multiple integration owners, automatic task scheduler

**Task Execution Manifest**:
The machine-readable YAML routing contract generated by `spec-package-generator` and consumed by the Spec Task Executor. It references the normative Task and related artifacts while owning their loading, dependencies, Skill Plan, validation, evidence destination, and freshness data without redefining behavior.
_Avoid_: Final prompt, copied context, informal handoff

**Execution Freshness Policy**:
The hybrid rule that digest-pins approved specification artifacts while requiring the Spec Task Executor to reread current project rules and assess their impact during Execution Preflight.
_Avoid_: Pin every source, trust every current file, ignore project-rule drift

**Skill Plan**:
The Task Execution Manifest section that classifies workflow Skills as mandatory, conditionally triggered, or executor-added. The Spec Task Executor may add justified Skills but cannot omit a mandatory Skill.
_Avoid_: Suggested Skill list, prompt hint, implicit Skill selection

**Execution Preflight**:
The human confirmation checkpoint before a Spec Task Executor modifies code. It approves the selected Task's internal Work Units, write ownership, Skill Plan, validation plan, and expected review scope without changing the approved Task itself.
_Avoid_: Specification gate, Task acceptance, implementation review

**Task Plan Gate**:
The human confirmation checkpoint after solution approval and before execution artifacts are finalized. It approves each Reviewable Capability, Shared Enabler, dependency, independent test boundary, and expected review scope.
_Avoid_: Gate 2 solution approval, Execution Preflight, Human Review Gate

**Approved Execution Boundary**:
The Task scope, Work Units, write ownership, Skill Plan, and validation plan authorized by an Execution Preflight. The Task Coordinator may work autonomously inside it until review-ready, but must stop when implementation would cross it or trigger a fail-closed state.
_Avoid_: General autonomy, specification change authority, implicit approval

**Execution Record**:
An append-only record of one Task Execution Session or Human Review revision, including its confirmed preflight, artifact versions, Work Units, Skill use, changes, validation, AI review, deviations, risks, and handoff state.
_Avoid_: Overwritten evidence, final summary, implementation-evidence index

**Integrated Task Validation**:
The Coordinator-owned validation of the complete Implementation-Ready Task after all Task Work Units are integrated. Focused Work Unit checks support it, but only this Task-level evidence can move the Task to review-ready status.
_Avoid_: Work Unit test result, individual agent success, partial validation

**Task Test Owner**:
The single writer responsible for establishing and validating the Task-level red-state acceptance expectations before implementation Work Units begin. Other workers may add focused tests but cannot weaken or independently redefine those expectations.
_Avoid_: Multiple acceptance-test owners, implementation-specific test writer, post-hoc test author

**Parallel Task Wave**:
A set of dependency-eligible Implementation-Ready Tasks executed concurrently as separate Task Execution Sessions.
_Avoid_: Task Work Units, concurrent edits without ownership, automatic task chain

**Human Review Gate**:
The mandatory pause after Task validation and AI code review have completed and all required findings are resolved. Only a human may accept the Task, and dependent development does not continue until acceptance.
_Avoid_: Automatic acceptance, AI self-approval, post-implementation summary

**Changes Requested**:
The Human Review Gate state in which an Implementation-Ready Task keeps its identity and returns for a focused revision against recorded review comments. Each revision appends validation and review evidence before returning to review-ready status.
_Avoid_: Blocked Task, replacement Task, overwritten review history

**Re-slice Required**:
The fail-closed state used when an Implementation-Ready Task is not cohesive or reviewable at its approved boundary. Only `spec-package-generator` may replace it with revised Task boundaries.
_Avoid_: Task Work Unit split, implementation workaround, blocked Task

**Spec Revision Required**:
The fail-closed state used when implementation evidence exposes missing, contradictory, or stale authoritative specification content. The Spec Task Executor returns control to `spec-package-generator` instead of redefining the specification.
_Avoid_: Re-slice Required, implementation assumption, silent scope change

**Spec Change Request**:
An evidence-backed handoff produced by the Spec Task Executor when Task boundaries or authoritative specification content must change. It identifies the affected Task, observed code evidence, return level, affected artifacts, and partial-change state so a human can explicitly start `spec-package-generator` revision.
_Avoid_: Automatic cross-Skill mutation, informal blocker note, executor-authored specification change
