# implement-spec-task

Execute one implementation-ready Task generated by `spec-package-generator`.
Require the path to that Task's YAML Task Execution Manifest. Do not accept a
legacy prompt-only package or reconstruct a missing Manifest.

Read [references/execution-contract.md](references/execution-contract.md)
before acting. Use the bundled templates for the preflight, Work Unit Briefs,
append-only Execution Records, and Spec Change Requests.

## Load And Qualify

1. Read the Manifest, its Task file, Task Plan Gate approval, readiness result,
   pinned normative artifacts, dependency states, and evidence destinations.
2. Re-read current applicable `AGENTS.md`, `CLAUDE.md`, `PROJECT_RULES.md`,
   architecture guidance, and ADRs. Never rely on rule text copied into a
   generated prompt.
3. Verify artifact digests, package readiness, human Task Plan confirmation,
   dependency acceptance, scope paths, and exactly one selected formal Task.
4. Fail closed without production-code edits when anything is missing, stale,
   contradictory, ineligible, or larger than the approved Reviewable
   Capability. Choose the matching terminal state from the execution contract.

## Run Execution Preflight

Inspect the current code and dynamically propose Task Work Units only for the
selected Task. Assign a Task Coordinator, one Task Test Owner, exclusive write
scopes, shared read-only inputs, a Skill Plan, Integrated Task Validation, and
an expected review-size summary.

Write or update the preflight artifact from
[templates/execution-preflight.template.md](templates/execution-preflight.template.md),
set the Task to `awaiting-preflight-approval`, present it to the human, and
stop. Do not modify production code before explicit human approval.

## Execute The Approved Task

After approval, set the Task to `in-progress` and operate autonomously inside
the Approved Execution Boundary:

- Apply `tdd` when behavior is testable through a public seam. The Task Test
  Owner establishes the correct Task-level red state before implementation
  workers begin and acceptance expectations must never be weakened.
- Use subagents only when the approved Work Units have exclusive ownership.
  Give each subagent a bounded Work Unit Brief, not the full package.
- Keep shared files single-writer under the Task Coordinator. Use read-only
  analysis, test, or review agents when write ownership cannot be isolated.
- Load every mandatory Skill in the Manifest. Load `codebase-design` when an
  interface, seam, adapter, dependency direction, or architectural
  responsibility changes. Record justified additional Skills and never omit a
  mandatory one.
- Amend non-material Work Unit details only when the Task boundary and
  exclusive ownership remain unchanged; otherwise renew Execution Preflight.
- Run Integrated Task Validation after integration. Then invoke `code-review`
  on the fixed Task change set, repair required findings, and rerun applicable
  checks.

Append an Execution Record for every execution or review-repair session. Update
`implementation-evidence.md` only as the convergence index and current summary.

## Stop For Human Review

When implementation and AI review pass, set the Task to `ready-for-review` and
provide the human handoff. Only the human may set `accepted`. Do not start the
next Task.

If review produces `changes-requested`, keep the same Task and Manifest, append
a new Execution Record, return to `in-progress`, and repeat validation and AI
review. If code evidence reveals a normative specification problem, create a
Spec Change Request and return the explicit `$spec-package-generator`
invocation; do not edit normative specification artifacts.
